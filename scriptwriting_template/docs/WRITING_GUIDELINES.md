# Writing guidelines

Use these guidelines when planning short-form technical explainers. They
complement `SCRIPT_STRUCTURE.md` and `SCRIPT_CONVENTIONS.md`; the schema and
validation command remain authoritative for JSON validity.

## Audience and explanation

- Assume the viewer is curious but has no formal computer-science background.
- Start with a familiar observation, concrete problem, or surprising claim.
- Explain one core mechanism accurately instead of replacing it with a vague
  metaphor.
- Define technical terms in the same breath that they are introduced.
- Name real components and processes when they matter to the explanation.

## Narration and pacing

- Keep scenes focused on one beat or idea.
- Prefer natural, conversational language over formal exposition.
- Use contractions and varied sentence lengths.
- Remove filler that does not advance the explanation or the joke.
- End with a clear payoff, useful consequence, or memorable twist.

## Visual-first writing

- Write narration that the available registry assets can support.
- Plan backgrounds, diagrams, characters, captions, and sound cues as part of
  the explanation rather than as decoration added afterward.
- Never invent an asset key. Flag a missing ideal asset and choose a supported
  alternative only when appropriate.
- Use transitions and pauses to support pacing, not to hide unclear structure.

## Workflow

Confirm the topic and creative direction before drafting the full JSON script.
Review the narration in scene order, then create the script in
`scripts/drafts/`, validate it, and generate a storyboard when visual review
is useful.
